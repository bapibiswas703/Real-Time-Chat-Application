# Verification and deployment readiness

Updated: 29 October 2026. This report records verified module behavior, security remediation and remaining deployment checks. Results identify their test environment and execution limits.

## Architecture and cleanup

The backend is one NestJS modular monolith with Auth, Users, Chats, Messages, ReadReceipts, Presence and Realtime modules. Each module has only the folders it needs: controller, service, repository, dto, utils or gateway. Shared SDK/connection providers live under `src/shared/`. Repositories are private providers; cross-module calls use exported services. Services expose business operations; repositories remain private to each module.

SQL access was moved into UsersRepository and ChatsRepository. MessagesRepository owns Firestore messages; ReadReceiptsRepository owns receipt/pointer persistence. Services retain caller/membership policy and workflow orchestration. DTOs were extracted from controllers. Transactions, canonical pair uniqueness, retry behavior, read semantics and all six chat API contracts are preserved. [Module layout and decisions](../architecture/modular-monolith.md).

Redundant architecture/progress documents were consolidated into the module guide. Local test runtimes/data, baseline snapshots, debug logs and generated coverage were removed after verification. Stale compiled output was removed before rebuilding. Installed dependencies and the current build are retained for local operation and ignored by Git. The ignored `.env` retains its local connection values and now references the ignored root `firebase-adminsdk.json` copy. The original downloaded credential is preserved. No production cloud settings, schemas, rules or indexes were changed.

## Security and reliability assessment

Firebase Phone/Google provider policy and revocation-aware verification remain unchanged. Every admitted private operation uses the verified user and current membership; tokens stay in a private session Map. Repositories do not bypass service authorization. Chat identity/membership constraints remain in PostgreSQL. Receipt/message reads and writes retain one Firestore transaction; callbacks do not emit events. Pure helper functions live in utils.

Presence remains approximate. The renewal budget assumes at most four Redis batches at five seconds each plus five seconds of scheduling inside the 30-second lease. Slow authorization/polling can intentionally disconnect clients. This is a design budget, not a production latency guarantee. Local counters/capacity reset across processes/reconnections; shared Redis fixed windows are not a global concurrency quota and direct peer addresses can aggregate clients behind proxies. [Budgets and protocol](../architecture/realtime-flow.md).

PostgreSQL, Firestore and Redis have no distributed transaction or durable outbox. Persisted success does not prove live delivery. History, stable IDs and retry keys remain the recovery authority; live packets never advance a durable history checkpoint. Remote revocation retains the verification-to-send race. Admin SDK IAM bypasses client rules; a single denied unauthenticated path is not a complete rules review.

## Deployment readiness

Deployment acceptance still needs actual Phone/Google sign-in/tokens, least-privilege cloud/SQL roles, rules/index review, measured load/outage behavior, Linux container/non-root/signal verification, backups/restore, TLS/ingress, alerting and rollout/rollback. Track the development advisory without forcing a toolchain downgrade.

The codebase uses conventional module folders and preserves chat behavior and authentication safeguards. Credential material and local runtime data are excluded from Git and Docker.
